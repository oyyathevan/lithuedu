🧪 Activity 4.1Unit IV

Develop a Low-Fidelity Prototype

⏱ 60 min👥 Individual / GroupConcept: BusPing

👨‍🏫 What the Student Should Do

  1. Pick one concept (BusPing) and one question to test.
  2. Build the cheapest version that answers that question (paper, role-play, cardboard phone).
  3. Do not polish — rough is better for honest feedback.
  4. Note what you left out and why.

🎨 Prototype Description — Model Answer

🎯 Question testedCan a student get a useful arrival time by sending one SMS/USSD code, without opening an app?
📦 What was builtPaper phone mock-up + handwritten “reply SMS” cards. Facilitator plays the system: student “sends” route code on paper; facilitator hands back a reply card with ETA.
⏱ Time taken~45 minutes

🧠 Reflection

1. Left out: Real network, GPS, multiple routes UI — only needed to test the “one message → one clear ETA” interaction.

2. Beyond a sketch: Watching someone hold the paper phone and wait for the reply shows hesitation, mis-typed codes, and whether the reply text is clear enough.

🧪 Activity 4.2Unit IV

Prepare a Storyboard

⏱ 45 min👥 IndividualPersona: Ravi Kumar

👨‍🏫 What the Student Should Do

  1. Use persona from Unit I (Ravi).
  2. Draw 6 panels: problem → steps with solution → outcome/feeling.
  3. Stay in the user’s view, not the designer’s.
  4. Keep 4–5 key moments only.

🎬 Panel Descriptions — Model Answer

1 · Trigger
Ravi checks the old app — time is wrong again; he risks missing class.
2 · Step 1
He opens Messages and sends the short code for his usual route (e.g. BUS12).
3 · Step 2
Within seconds he gets a reply: “Bus 12 · ~8 min · Gate stop”.
4 · Step 3
He finishes tea, leaves home at the right moment, walks calmly to the stop.
5 · Step 4
Bus arrives close to the ETA; he boards without running.
6 · Outcome
Reaches college on time, feels less anxious — “I can trust this.”

🧠 Reflection

1. Hardest panel: Panel 3 — making the reply message short and clear enough to show in one frame.

2. Gap revealed: What if the student doesn’t know the route code? Need a simple way to learn/save codes.

🧪 Activity 4.3Unit IV

Build a Physical / Digital Prototype

⏱ 90 min👥 GroupType: Digital + role-play backend

👨‍🏫 What the Student Should Do

  1. Pick Physical or Digital (or hybrid).
  2. Build only one complete task flow.
  3. Keep fidelity just high enough for a real user to try the task.
  4. Record build time and approximate cost.

🔧 Prototype Summary — Model Answer

🏗 TypeDigital (clickable phone mock) + role-play SMS backend
🎯 Flow coveredOpen messages → type route code → send → receive ETA reply → decide when to leave
⏱ Build time~75 minutes
💰 Cost≈ ₹0 (paper + free Figma-style screens / phone mock)

🧠 Reflection

1. Harder than expected: Writing reply text that feels real and fits one SMS line.

2. v2 will improve: Saved favourite routes so the user does not retype the code every time.

🧪 Activity 4.4Unit IV

Conduct User Testing

⏱ 60 min👥 Group# Testers: 3

👨‍🏫 What the Student Should Do

  1. Recruit 3–5 real users (not only close friends).
  2. Give 2–3 tasks; do not help when they struggle.
  3. Log time, errors, and notes for each tester.
  4. Watch more than explain.

🎯 Tasks Given — Model

  1. Find out when Bus 12 will reach the Gate stop.
  2. Decide whether you should leave home now or wait 10 minutes.
  3. Save or remember the code so you can use it again tomorrow.

📝 Test Log — Model Answer

Tester 1Time: 1:40 · Errors: 1 (wrong code format) · Notes: Asked “Do I need spaces?”
Tester 2Time: 1:10 · Errors: 0 · Notes: Understood reply immediately; wanted “leave by” time.
Tester 3Time: 2:05 · Errors: 2 · Notes: Tried to open an app first; later succeeded with SMS.

🧠 Reflection

1. Most struggle: Knowing the exact code format (spaces / uppercase).

2. Unexpected: Several wanted a “leave by HH:MM” suggestion, not only “arrives in X min”.

🧪 Activity 4.5Unit IV

Collect Structured Feedback

⏱ 30 min👥 IndividualPrototype: BusPing v1

👨‍🏫 What the Student Should Do

  1. Group test notes into themes.
  2. Mark severity: 🔴 high · 🟡 medium · 🟢 low.
  3. Write a concrete recommendation for each theme.
  4. Pick Top 3 fixes for v2.

📊 Feedback Themes — Model Answer

1Theme: Code format unclear · 🔴 High
Rec: Accept flexible input; show example “BUS12” on first use.
2Theme: Want “leave by” time · 🟡 Medium
Rec: Add optional line: “Leave by 7:42 if walking 8 min.”
3Theme: Habit of opening apps · 🟢 Low
Rec: Poster at hostel: “Text BUS12 — no app needed.”
4Theme: Saving the code · 🟡 Medium
Rec: Reply includes “Save this number as BusPing.”

🎯 Top 3 Fixes for v2

  1. Flexible code parsing + example on first reply.
  2. “Leave by HH:MM” line when walk time is known.
  3. Prompt to save the service number as a contact.

🧠 Reflection

1. Most surprising: Users wanted leave-by time more than a prettier map.

2. Ignore for now: Full multi-language support — important later, not blocking the core test.

🧪 Activity 4.6Unit IV

Modify the Prototype

⏱ 60 min👥 GroupPrototype: BusPing v2

👨‍🏫 What the Student Should Do

  1. Apply only the Top 3 fixes from 4.5.
  2. Do not add random new features.
  3. Document each change and why.
  4. Photograph or note before/after if possible.

🔧 V1 → V2 Changes — Model Answer

1Change: Accept BUS12, bus12, Bus 12 · Why: Testers mistyped format.
2Change: Reply adds “Leave by 7:42 (8 min walk)” · Why: Users asked for decision support.
3Change: First reply ends with “Save this number as BusPing” · Why: Repeat use was friction.

🧠 Reflection

1. Most impactful: Flexible codes — fewer errors in a quick re-test.

2. Not changed: Live map UI — out of scope for SMS concept; would dilute the core test.

🧪 Activity 4.7Unit IV

Prepare an Iteration Log

⏱ 30 min👥 IndividualProject: BusPing

👨‍🏫 What the Student Should Do

  1. List each version: change, reason, result.
  2. Include failures — they teach more than wins.
  3. Write a short 3-sentence project summary.
  4. Start the log early; do not rely on memory later.

📓 Iteration Log — Model Answer

v1Change: Paper + role-play SMS · Reason: Test core “one code → ETA” · Result: Concept understood; code format errors
v2Change: Flexible codes + leave-by + save prompt · Reason: Top 3 fixes from tests · Result: Faster completion, fewer errors
v3Change: Example in first reply (“Try: BUS12”) · Reason: New users still guessed · Result: First-time success improved
v4Change: Optional walk-time input once · Reason: Leave-by needs distance · Result: More useful decision support

📄 3-Sentence Summary

BusPing helps college students get a real bus ETA by sending one short code, without relying on inaccurate apps. Low-fi tests showed the idea works, but code format and “when should I leave?” needed fixes. After three iterations, users complete the task faster and report less morning anxiety about missing the bus.

🧠 Reflection

1. Most teaching iteration: v1 → v2 — real users exposed assumptions we could not see in sketches.

2. Why document: Teams forget why a change was made; the log keeps evidence for reports and future members.
